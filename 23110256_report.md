## Phase 1

I disassembled `phase_1` with `objdump -d` and saw it load a constant address `0x40217a` into
`%esi` and my input into `%rdi`, then call `strings_not_equal`. It clicked at the `test %eax,%eax`
and `je` after the call: the jump past `explode_bomb` is taken only when the return value is 0, and
since the function is named *not* equal, 0 means the strings matched. I read the string with
`objdump -s -j .rodata bomb`, found row `402170`, and counted 10 bytes in. The ASCII column ends in
`ter.` but the hex is `74657200`, so that dot is a NUL, not a period. Answer: `Segfaults build
character`. I confirmed it with `x/s` in gdb.

## Phase 2

The `sscanf` call here loads its format string from `0x402194`. My first mistake was lazy: I had the
`.rodata` dump open from phase 1, saw `25642025 64` = `%d %d` sitting at `0x4021a0`, and typed two
numbers. Boom. The two format strings *overlap* -- `0x402194` is the full `%d %d %d %d %d %d` and
`0x4021a0` is just its tail, reused by the later phases. The `cmp $0x6,%eax` right after the call
would have told me that immediately if I had read forward instead of guessing.

The loop is textbook: `-0x4(%rbp)` is `i`, initialised to 1, and `cmpl $0x5,-0x4(%rbp)` / `jle` at
the bottom runs it while `i <= 5`. Inside, `%edx` gets `a[i]` from `-0x20(%rbp,%rax,4)` and `%eax`
gets `a[i-1]`. The moment it clicked was `add %eax,%eax` followed by `add $0x1,%eax` -- I first read
the doubling as a square, but `a+a` is `2a`, so the constraint is just `a[i] == 2*a[i-1] + 1`.
Nothing constrains `a[0]`, so I started at 1: `1 3 7 15 31 63`.
